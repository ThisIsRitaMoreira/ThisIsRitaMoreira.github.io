How I work

Different industries, one way of working.

I've worked with HR tickets, supermarket orders, airline schedules and truck sensors. The data changed every time. The way I work didn't.

Start from the decision

Before I touch any data, I ask who will use the answer and what they will decide with it. At Intermarché, that meant a list of what each section should order, not a report of last week's sales.

Get the data right

Next, I check the data: missing values, duplicates, records that don't match between systems. When ALTEN acquired a 700-person company, its HR records had to be matched to ALTEN's format before any report could be trusted.

Find the pattern

Then I look for what explains the problem: which tickets keep coming back, which employees are more likely to leave, which late flights delay the rest of the day. I pick the tool that fits, whether that's SQL, Python, R or Power BI.

Translate it

Finally, I turn the results into something people can act on: a short list, a simple dashboard or a clear recommendation, in the team's own words. My background in languages helps here.

-- Weekly SLA compliance and volume, one row per team and week
WITH final_state AS (            -- the log has one row per update: keep the last one
  SELECT *, ROW_NUMBER() OVER (PARTITION BY number ORDER BY sys_mod_count DESC) AS rn
  FROM incident_event_log
)
SELECT assignment_group                              AS team,
       DATE_TRUNC('week', opened_at)                 AS week,
       COUNT(*)                                      AS tickets,
       AVG(CASE WHEN made_sla THEN 1.0 ELSE 0 END)   AS sla_met_rate,
       PERCENTILE_CONT(0.5) WITHIN GROUP (
         ORDER BY EXTRACT(EPOCH FROM resolved_at - opened_at) / 3600) AS median_hours
FROM final_state
WHERE rn = 1 AND opened_at >= '2016-03-01' AND opened_at < '2016-06-01'
GROUP BY 1, 2
ORDER BY 1, 2;

-- Backlog at the end of a given day = opened before, not yet resolved
SELECT COUNT(*) AS open_tickets
FROM final_state
WHERE rn = 1 AND opened_at < :day_end AND COALESCE(resolved_at, closed_at) >= :day_end;

Chapter 2

Why tickets come back, and what fixing it is worth

Real dataWhat-if model

A repeat ticket is the same person coming back about the same category within 14 days, or rejecting the resolution. Repeats are expensive: the desk does the work twice and the employee loses trust. To act on them, you need to know where they cluster and which fix works.

Repeat-ticket drivers
Where repeats cluster
Repeat tickets by category, with the running share of all repeats. Categories are anonymized in the source.
What works: a knowledge article
Repeat rate when the resolver used a knowledge-base article vs. when they didn't.
What-if: publish knowledge articles for the top repeat drivers
Covered categories get the repeat rate seen when an article was used, for the share of tickets where it gets used.

Caveat, stated up front: resolvers chose when to use an article, so this comparison is observational, not a controlled test. In a live rollout I'd confirm the effect with a before/after comparison on the covered categories against the uncovered ones.

Defining a repeat ticket
-- A ticket is a repeat if the same requester opened one in the same category
-- in the previous 14 days, or rejected the resolution (reopen_count > 0)
SELECT number, caller_id, category, opened_at,
       CASE WHEN reopen_count > 0
              OR opened_at - LAG(opened_at) OVER (
                   PARTITION BY caller_id, category ORDER BY opened_at) < INTERVAL '14 days'
            THEN 1 ELSE 0 END AS is_repeat
FROM tickets;
# what-if: cover the top-N repeat categories with a knowledge article
def simulate(cats, n_covered, adoption, kb_rate_team):
    saved = 0
    for c in cats[:n_covered]:
        rate_without = c.rep_nokb / c.n_nokb
        rate_with = c.rep_kb / c.n_kb if c.n_kb >= 30 else kb_rate_team   # small-sample guard
        saved += c.n_nokb * adoption * max(0, rate_without - rate_with)
    return saved / total_repeats          # share of repeat tickets avoided

The problem

In a supermarket, each section manager (dairy, drinks, fresh meat…) orders thousands of products, often from memory and last week's sales. Forecast Next Week =

All 140 products replayed week by week on real demand. "Habit" = order up to 2× last week's sales. "Recommended" = the logic above.
Order logic (also runs in this page's JavaScript)
def recommend(base, lift, promo_next, promo_after, sd, on_hand, pack, moq_cases=1, z=1.65):
    f1 = base * (lift if promo_next else 1)          # week the order covers
    f2 = base * (lift if promo_after else 1)         # + one week of lead time
    safety = z * sd * (2 ** 0.5)                      # review + lead time = 2 weeks
    need = max(0, f1 + f2 + safety - on_hand)
    cases = math.ceil(need / pack)
    if 0 < cases < moq_cases:
        cases = moq_cases                             # supplier minimum
    return cases * pack

' Decision cells : cases ordered (whole numbers) and units sold, for each of the 12 products
' Objective      : maximize  SUM( margin × units sold )  −  SUM( leftover cost × units left over )
' Constraints    : units sold   ≤ forecast demand            (can't sell more than shoppers want)
'                  units sold   ≤ cases × case pack           (can't sell what wasn't ordered)
'                  cases        ≥ supplier minimum
'                  cases          integer
'                  SUM( cases × case pack × unit cost )  ≤ $1,200   (budget)

# 03_gold_kpis: one function, used per airline, per month and combined
def kpis(df, keys):
    arr = F.col("arrived")
    return df.groupBy(*keys).agg(
        F.count("*").alias("flights"),
        F.sum((F.col("status") == "cancelled").cast("int")).alias("cancelled"),
        F.avg(F.when(arr, F.col("a14").cast("int"))).alias("a14"),     # on time = 14 min late or less
        F.avg(F.when(arr, F.col("arr_delay_min"))).alias("avg_arr_delay_min"),
        F.sum(F.coalesce(F.col("late_aircraft_delay_min"), F.lit(0))).alias("late_aircraft_min"))

save(kpis(legs, ["carrier", "month"]).withColumn("merger_phase", phase), "gold_carrier_month_kpi")

The problem

A threshold flags, it doesn't prove

The insurer's rule is simple: abnormal driving events per million miles, with an alert at 7.0. Our pipeline flagged 7 of 25 drivers. The fleet manager's next question is the real one: do all seven go to safety training? And is the problem the people, or the trucks?

A driver with few events can cross 7.0 on one bad stretch. So after the pipeline and the dashboard, we tested every flag with three Python models. Only 4 of the 7 held up, and risk followed the driver, not the truck.

The risk factor, computed in Hadoop
-- risk_factor.pig: run with  pig -useHCatalog -f risk_factor.pig
a = LOAD 'geolocation' USING org.apache.hive.hcatalog.pig.HCatLoader();
b = FILTER a BY event != 'normal';                          -- abnormal events only
c = FOREACH b GENERATE driverid, event, (int) '1' AS occurance;
d = GROUP c BY driverid;
e = FOREACH d GENERATE group AS driverid, SUM(c.occurance) AS t_occ;
g = LOAD 'driver_mileage' USING org.apache.hive.hcatalog.pig.HCatLoader();
h = JOIN e BY driverid, g BY driverid;
final_data = FOREACH h GENERATE $0 AS driverid, $1 AS events, $3 AS totmiles,
             (float) $1 / $3 * 1000000 AS riskfactor;      -- events per million miles
STORE final_data INTO 'riskfactor' USING org.apache.hive.hcatalog.pig.HCatStorer();
-- Written to run unchanged in Hive 1.x and Impala
SELECT driverid,
       events,
       totmiles,
       ROUND(riskfactor, 2) AS risk_score,
       CASE WHEN riskfactor >= 7.0 THEN 'ALERT' ELSE 'Below threshold' END AS status
FROM   riskfactor
ORDER BY risk_score DESC
LIMIT 25;

What I'd do

Recommendations

Act on four, monitor three

Targeted coaching for the four drivers the model is sure about; re-score A88, A54 and A20 next quarter instead of acting on one number.

Coach people, don't replace trucks

Risk follows the driver across vehicles, so maintenance spending won't move the score.

Onboard new licence holders and contractors more closely

The aggressive profile is drivers with a licence under 2.5 years, and both contractors are on the alert list.

Add a 65 mph alert

A plain speed rule flags 1.8% of pings and still catches 42% of events: a cheap first line before any model.
